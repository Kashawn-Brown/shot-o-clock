## D001 — Package manager: npm
Decided 2026-05-13. Use npm — CLAUDE.md already references `npm view` / `package-lock.json` and there's no monorepo pressure to justify pnpm. Would revisit only if the repo grows into a multi-package workspace.

## D002 — Expo template: default
Decided 2026-05-13. Bootstrap apps/mobile with create-expo-app's `default` template (TypeScript + Expo Router pre-wired) over blank-typescript, which would mean wiring the router by hand. Its demo content is throwaway and was replaced early.

## D003 — Stay on Expo SDK 54
Decided 2026-05-13. Keep SDK 54 (what create-expo-app shipped) rather than force-upgrading to 55, because the template/SDK pairing the Expo team bundles is the most coherent starting point. Revisit with an explicit upgrade task once the bundled template catches up to 55.

## D004 — Path-alias coexistence with template dirs
Decided 2026-05-13. Add REPO_STRUCTURE.md aliases (`@/features/*`, etc.) alongside temporary template-fallback targets so existing template imports don't break mid-phase. The fallbacks self-clean when template dirs are restructured (happened early via D006).

## D005 — Prettier rules beyond CLAUDE.md §5.2
Decided 2026-05-13. For the rules §5.2 left open, pin `printWidth: 100`, `arrowParens: always`, `endOfLine: auto`. `endOfLine: auto` is load-bearing — without it `format:check` fails on Windows CRLF checkouts.

## D006 — Delete template demo code, don't reformat it
Decided 2026-05-13. Delete the Expo template's demo screens/components/assets now and ship a minimal placeholder, rather than burning commits reformatting throwaway code to pass `format:check`. Keeps the tree honest about what's real MVP code.

## D007 — Keep EXPO_PUBLIC_SUPABASE_ANON_KEY name
Decided 2026-05-13. Keep the env var named `…ANON_KEY` even though the Supabase CLI now emits `sb_publishable_`. No downstream consumers exist yet and "anon key" matches every supabase-js tutorial. Rename if Phase 1/2 confusion recurs or the SDK deprecates the term.

## D008 — RLS in one migration file
Decided 2026-05-13. Put RLS helpers and policies together in a single `_rls.sql` (separate from `_initial_schema.sql`), not three files. The four helpers' only callers are the policies, so splitting them yields a file with no standalone consumer.

## D009 — Scope RLS policies TO authenticated
Decided 2026-05-13. Scope every SELECT policy `TO authenticated` rather than relying on Postgres's PUBLIC default, and update rls-rules.md to match. Behavior is identical (helpers already check auth.uid()) but intent is explicit; anonymous-auth guests are still `authenticated`.

## D010 — Phase 2 RPC infrastructure conventions
Decided 2026-05-13. Lock the conventions every later RPC copies: `SET search_path = public, pg_temp` on all SECURITY DEFINER functions; read RPCs do their own auth.uid()+membership check (DEFINER bypasses RLS); internal helpers REVOKE EXECUTE from public/anon/authenticated; §13 reads conform to the standard `{ok,error_code,error_msg,data}` envelope; the supabase client is pulled forward from Phase 3.

## D011 — Batch B1 conventions (create_party + join_party)
Decided 2026-05-14. plpgsql random-index join-code generation with collision retry; `ALREADY_HOSTING` includes `paused`; `phase_started_at` set at create; join codes are permanently consumed (column-level unique kept, §2.5 tightened); reconnect (§3.6) is checked before §3.4 preconditions.

## D012 — Batch B2 conventions (leave_party + end_party)
Decided 2026-05-14. leave_party sets both `removed_at` and `left_at`; success `data = {}`; end_party's timer_event is `triggered_by = host`, preserves pause columns as history, and nulls `phase_ends_at`. Adds a new `round_cancelled` value to the timer_event_type enum so a cancelled round isn't mislabeled `round_completed`.

## D013 — leave_party for kicked callers returns PLAYER_REMOVED
Decided 2026-05-14. A previously-kicked caller (status=removed, removed_reason ≠ self_left_lobby) calling leave_party gets `PLAYER_REMOVED`, not idempotent ok — so the UI can distinguish "you were kicked" from "you left." Idempotent ok is reserved for genuine self-leaves.

## D014 — Auto-advance rounds; remove start_next_round
Decided 2026-06-03. Rounds auto-advance (shot_window → round_complete → countdown(N+1)) atomically inside the finalizing RPC via a shared `finalize_round_outcomes` helper; the host-gated `start_next_round` RPC is removed from MVP. `round_complete` stays in the enum as a transitional pass-through — and as the real resting state when finalization leaves zero active players, which halts for host intervention. Two ordered timer_events are still emitted. Supersedes state-machine §10's "start_next_round is host-triggered." Would change if the product ever wants a manual host gate between rounds.

## D015 — Batch E host-control conventions
Decided 2026-06-04. Three forks resolved before writing the 8 host-control RPCs. (1) **Shared helper:** the D014 auto-advance tail (create round N+1 / zero-active halt) is extracted from `finalize_round_outcomes` into a new internal `advance_to_next_round` helper, and `finalize_round_outcomes` is re-pointed at it via create-or-replace (E0, no behavior change). This lets `host_mark_player_active` re-trigger the auto-advance out of the zero-active `round_complete` halt without routing through `finalize_round_outcomes`, whose `completed_at` gate returns before the tail. (2) **timer_events emission:** `host_pause_timer`/`resume`/`add_time` emit `timer_paused`/`timer_resumed`/`time_added` events in addition to the `admin_action_logs` rows §10 names — the enum values exist for exactly these actions and keep the timer timeline reconstructable. (3) **Lobby guard:** `host_mark_player_out`/`active` require `current_round_number >= 1`, else `ILLEGAL_TRANSITION` — marking out at round 0 would trip the `out_round_number >= 1` CHECK; both are mid-game actions. Also locked: pause uses option (a) (store `paused_remaining_seconds`, never mutate `phase_ends_at`); `host_skip_to_shot_window`/`host_end_shot_window` require `status = active` (paused → `ILLEGAL_TRANSITION`, per state-machine §4); player-override RPCs take the target `party_player_id` and return `PLAYER_NOT_FOUND` before `NOT_HOST`. Would change if the product adds a manual host gate between rounds or exposes overrides in lobby.

## D016 — Age/terms: first-launch gate + per-join checkboxes
Decided 2026-06-04. Confirm legal age + responsible-use via BOTH (a) a one-time first-launch gate that renders after auth and before the navigator, covering host and guest, with flags persisted device-local in SecureStore (no DB write — `terms_acceptances` is a reserved/future table, schema.md §10); AND (b) per-join checkboxes on the Join Party screen (matches Figma, point-of-action reaffirmation, local form state with no persistence — reset each visit). Pure per-join checkboxes (Figma-only) were rejected: the host's create-party path never passes through Join, so it would leave the host's age/terms unconfirmed. plan.md's "first launch gates, second launch skips them" still holds for the gate. Would change if the product drops one of the two paths.

## D017 — Display name captured at first launch, reused as guest identity
Decided 2026-06-04. The display name is captured once on first launch (NameEntryGate, after the age/terms gate) and persisted device-local in SecureStore. It serves as the host's name on Create (which has no name field — confirming the intent) and prefills the Join screen's Display Name field, which stays editable for per-party aliasing. Validated 1–40 code points to mirror the create_party/join_party DB CHECK (schema.md:183). On-form-only capture was rejected because Create has no host-name field; locking the Join field was rejected to allow per-party names. Would change if a profile/account flow later owns the name.

## D018 — Shared-device guests share one identity (known limitation)
Decided 2026-06-04. Guest identity (display name), consent flags, and the anonymous Supabase session are all stored device-local (SecureStore + the persisted supabase session, per D016/D017). Two people sharing one physical device therefore share the same guest identity, consent, and session — there is no per-person separation for guests. Accepted for MVP. Planned fix: a "Reset this device" option in the Settings screen (plan.md Phase 12) that clears the stored identity, consent flags, and anonymous session, returning the device to a fresh first-launch flow for the next person. Would change if accounts/profiles land and guests can claim or switch identities.

## D019 — Party album (post-MVP feature design)
Decided 2026-06-08. Locks the product design for the post-MVP party-album feature (out of MVP scope per CLAUDE.md §4.2 — recorded now so the decision isn't lost). **Album creation:** automatic, no host opt-in — auto-creates on the first media capture/upload by any participant; if nobody captures, no album exists and nothing is shown; host cannot prevent creation but holds full post-creation moderation. **Camera button:** always visible to all participants during the game (timer, shot window, results screens) and after game end until party close; no permission gate; primary action is in-app live capture (photo/short video), with a de-emphasized secondary "upload from camera roll." **First-capture popup:** informational (not a decision gate) — explains the item saves to this party's album and is visible to everyone; proceed/cancel; consent through information. **Upload window:** open from first capture until the host closes the party — End Game (stops rounds) and Close Party (locks the album) are two separate host actions; auto-close 24h after game end if the host never closes manually. **Attribution:** every upload shows who captured it. **Media controls:** a participant can delete only their own uploads while the party is open; the host can delete any single item at any time, including after close; the host can delete the whole album; no new uploads after close. **Access:** game participants only — no after-the-fact joining, no public albums. **User education:** the rules/how-to-play screen explains the camera button and that photos are saved to a shared party album; no tutorial beyond the first-capture popup. Open question (#007): whether camera-roll uploads carry authenticity constraints (e.g. media must be from that night) — undecided.

## D020 — RLS membership helpers are SECURITY DEFINER (recursion fix)
Decided 2026-06-08. The four membership helpers (`is_party_member`, `is_active_party_member`, `is_party_host`, `my_party_player_id`) are `SECURITY DEFINER` with a pinned `search_path`, not `SECURITY INVOKER` as originally written in Phase 1. As INVOKER they query `party_players`, and the `party_players` SELECT policy calls them — so the helper's internal read re-triggered `party_players` RLS across a function-call boundary and recursed without bound, overflowing the stack (`54001 stack depth`, which Postgres's `42P17` direct-recursion detector can't catch through a function). Every authenticated party-table read hit this; `getActiveParty`'s launch read of `party_sessions` was simply the first to surface it (the app's first authenticated client SELECT through RLS — Phase 2 RPCs are DEFINER and bypass it). DEFINER makes the internal read bypass RLS and terminates the recursion; safe because each helper returns only a boolean / the caller's own `party_player_id` about `auth.uid()`'s own membership. This is the Supabase-recommended pattern for membership checks used inside RLS policies. Fixed in migration `20260608120000_fix_rls_helper_recursion.sql`; verified at the DB level (helpers `prosecdef = t`; an authenticated SELECT on `party_sessions`/`party_players` returns rows with no overflow). rls-rules.md §1.4 + §12 updated. Would change only if a helper ever needed to return data beyond the caller's own membership (it shouldn't).

## D021 — Late joining (post-MVP)
Decided 2026-06-08. MVP is lobby-only join (`allow_late_join = false`; the new-join path requires `current_phase = lobby` per rpc-contracts §3.4). Post-MVP plan: allow late joining as an active player. A late joiner starts their shot tally from the round they joined (not retroactively), and grace logic applies from their first round forward. The data model already supports it — `party_settings.allow_late_join` exists and is wired false for MVP. The hard part is UX, not schema: what a late joiner sees landing mid-countdown vs mid-shot-window, and how their "joined late" state reads in the roster. Out of MVP scope; revisit when late join is built.

## D022 — Out-player notification prompt + spectator state (post-MVP)
Decided 2026-06-08. When a player goes out, show a one-time prompt — "Still want Shot O'Clock alerts?" with **Stay Notified** / **Turn Off** — changeable anytime while the game runs. Out players remain spectators: they can still see the synced timer and the full-screen Shot O'Clock screen, but the **Done** button is disabled and **I'm Out** is replaced with a passive "You're out — watching" state. Post-MVP: notifications are explicitly out of MVP scope (CLAUDE.md §4.2), and the per-player notification table (`party_player_notification_settings`) is reserved/unused in MVP. The in-game spectator framing (out players watching, Done disabled) informs the Phase 8 Shot O'Clock screen even before notifications land.

## D023 — Roster row shows name + shot count + status (Phase 6+ reference)
Decided 2026-06-08. Each player row in the roster/standings view should show: display name, individual shot count, and status (active / out / used grace / joined late, etc.). The data already exists — `party_players.total_shots_completed` for the count and `round_player_outcomes` for per-round status detail. Not a behavior change; a reference note for the Phase 6+ roster build-out so the row design accounts for all three fields from the start rather than retrofitting.

## D024 — join_party lets a self-left player rejoin; host-kick stays blocked
Decided 2026-06-08. Bugfix found in Phase 5 testing: `join_party`'s reconnect branch returned `PLAYER_REMOVED` for any `status = 'removed'` row, so a player who voluntarily left the lobby (`leave_party`, `removed_reason = 'self_left_lobby'`) could never rejoin with the same code. Fix: branch on `removed_reason` — only an exact `'self_left_lobby'` may rejoin; everything else stays `PLAYER_REMOVED`. The test is a whitelist (`IS DISTINCT FROM 'self_left_lobby'`) because `host_remove_player` sets `removed_reason` to a free-text value **or null** ("still reads as kicked"), so a null must remain blocked. A self-left rejoin is treated as a fresh join, not a live reconnect: it applies the §3.4 preconditions (lobby + not locked, since late join is off in MVP), restores the existing row to active (clearing the removal fields, refreshing timestamps, adopting the new `display_name`), and returns `is_reconnect = false`. Self-left only happens in lobby, so no in-game data is resurrected. Extends D013's self-left-vs-kicked distinction (established for `leave_party` idempotency) to the join path. Fixed in migration `20260608130000`; rpc-contracts.md §3.6 updated. Would change if late join lands (the lobby-only precondition would relax).

## D025 — Mid-game settings adjustments (post-MVP)
Decided 2026-06-09. Post-MVP, the host may change certain party settings while the game is running. **Adjustable mid-game:** shot window length and interval increment. **Not adjustable mid-game:** grace mode and elimination mode — both affect how past rounds were scored, so changing them mid-game would retroactively rewrite outcomes already recorded in `round_player_outcomes`. All mid-game changes apply **from the next round forward, not retroactively** — the current round finishes under the settings it started with. In host-controlled manual shot window mode ([[D026]]), shot window length is irrelevant mid-game (there is no countdown to resize), so only interval increment is meaningfully adjustable there. Out of MVP scope (CLAUDE.md §4.2 keeps host controls to the locked set); recorded now so the next-round-forward boundary is settled before any settings-mutation RPC is designed. Would change if the product decides some setting should apply to the in-flight round.

## D026 — Host-controlled manual shot window mode (post-MVP)
Decided 2026-06-09. A party setting the host enables **at creation time** (not toggleable mid-party). When enabled, the shot window has **no countdown timer**: Shot O'Clock fires, players take their shot at their own pace and tap **Done** or **I'm Out**, and the host manually taps **End Shot Window** to close the round. No timer pressure on players. The host sees a **count-up** (how long the window has been open) for awareness; players do not see it. **Grace logic still applies normally** — a player who hasn't tapped Done when the host ends the window is scored as a miss, exactly as in timed mode. The `shot_window_length` setting is **ignored** in this mode. Implementation is small: the `host_end_shot_window` RPC already exists and performs the close (it reuses `finalize_round_outcomes`); the additions are (a) a new party setting persisted at create, and (b) the UI change — suppress the player countdown, show the host count-up, and require the host's manual End Shot Window tap to advance. Out of MVP scope. Would change if the product wants a host-toggle mid-party or a fallback auto-close timeout on top of manual mode.

## D027 — Lobby realtime roster: re-fetch on event, not payload patching
Decided 2026-06-09. The lobby's live roster subscribes to `party_players` `postgres_changes` (filtered by `party_session_id`) but, on every event, **re-fetches the authoritative `get_party_state` snapshot** rather than splicing the event's row payload into local state. Two reasons: (1) `get_party_state` already applies the dual-visibility rules (members see non-removed peers; host sees all; you always see your own row — `rls-rules.md` §4), which a client-side payload patch would have to re-implement and keep in sync; (2) realtime delivery is itself RLS-gated per subscriber, so a non-host never *receives* a peer's removal UPDATE (they can't SELECT a removed row) — meaning payload-only patching would silently miss removals. The event is treated as a "something changed, re-pull the truth" trigger. Refreshes are **silent** (no spinner, last-good roster retained on transient failure) to avoid flicker on each join. A refresh returning `SESSION_NOT_FOUND` is the signal that the caller themselves was removed (RLS now hides the session) → the screen routes home (`membershipLost`). Requires `party_players` in the `supabase_realtime` publication (migration `20260609120000`; `schema.md` §15). Trade-off: one extra round-trip per event, negligible at lobby scale. Would change if payload volume ever made the re-fetch costly (then patch the common INSERT/UPDATE cases and reconcile periodically).
